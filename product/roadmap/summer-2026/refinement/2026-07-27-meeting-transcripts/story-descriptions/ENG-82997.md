## Description (paste-ready)

Per ENG-82991. UI for the **AI Recap card** — the read-only, post-meeting summary surface. This ticket renders the recap payload produced by the AI platform (ENG-82387); it contains **no generation logic**. The recap is **persona-agnostic** — both participants see the identical card. Content is transcript-grounded; PII is handled upstream in the AI inference step.

Schema (locked 6/25): **Summary / Blockers (≤3) / What-Happened / Follow-ups (≤5)**, caps scale with meeting duration; no "AI Suggested" header. What-Happened items are grouped under semantic labels (Decided / Agreed / Open Risk); Blockers show owner + priority; Follow-ups show owner.

**Past-meeting placement:** for a past/Completed meeting the meeting page presents a **top tab bar** — Overview / Shared Notes / Private Notes / AI Transcripts — and the Recap is surfaced within the **Overview** tab. (The tab relayout itself may be shared with the meeting-page-layout story; ACs here cover Recap placement within it.)

**Acceptance Criteria**

1. **Availability** — *Given* transcript processing is complete in Active state, *When* the user opens the meeting, *Then* the Recap card renders in the main panel; *And* it is not shown in Upcoming or while processing is in progress.
2. **Past-meeting placement** — *Given* a past/Completed meeting, *Then* the meeting page shows a top tab bar (Overview / Shared Notes / Private Notes / AI Transcripts), *And* the Recap is surfaced within the Overview tab.
3. **Persistence** — *Given* the meeting is Completed, *Then* the Recap card remains available and does not expire.
4. **Read-only** — *Given* the Recap card is shown, *Then* no section is editable in any state.
5. **Schema render** — *Given* a recap payload, *Then* the card renders, in order: Summary, Blockers (max 3), What-Happened, Follow-ups (max 5); *And* the caps scale with meeting duration as supplied in the payload.
6. **What-Happened grouping** — *Given* What-Happened items, *Then* they are grouped under the semantic labels supplied in the payload (Decided / Agreed / Open Risk).
7. **Item attribution** — *Given* a Blocker item, *Then* it shows an owner and a priority (e.g. High / Medium); *Given* a Follow-up item, *Then* it shows an owner.
8. **No header** — *Given* the Recap card is shown, *Then* no "AI Suggested" header or label appears.
9. **Collapsible** — *Given* the Recap card is shown, *When* the user toggles the card header (Show more / Show less), *Then* the card expands or collapses.
10. **Persona-agnostic** — *Given* both participants, *When* either opens the meeting, *Then* each sees the identical recap content.
11. **Inline evidence** — *Given* a recap item carries an evidence excerpt, *Then* the excerpt is shown inline on the card, *And* no redirect to the Transcript tab is required.
12. **Open in Zoom** — *Given* a Zoom recording is available for an item, *Then* an "Open in Zoom" link is shown alongside the excerpt.
13. **Quality signals** — *Given* the card is shown, *When* the user selects thumbs-up, thumbs-down, or flag, *Then* the signal is captured; *And* thumbs-down optionally prompts a freetext note; *And* flag offers: wrong speaker, inaccurate summary, missing content, other.
14. **Loading** — *Given* transcript processing is in progress, *Then* a skeleton is shown in the Recap card area.
15. **Empty** — *Given* processing completed but content was insufficient, *Then* a quiet empty state is shown ("Not enough content to generate a recap for this meeting") with no error treatment.
16. **Error** — *Given* processing failed, *Then* an unobtrusive inline message is shown without blocking other meeting content.
